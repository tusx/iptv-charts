# IPTV Charts 0.8.0 implementation contracts

This file is the frozen interface for the 0.8.0 release. Read the approved
plan at `/home/tusx/.claude/plans/temporal-enchanting-naur.md` for product
context. Feature agents must not change these contracts without an integration
decision.

## 1. Schema v5

`db.SCHEMA_VERSION = 5`. A fresh database and a v4 upgrade must converge on the
same state.

### Profiles

`quality_profiles` keeps its legacy columns for migration/read compatibility,
and adds:

- `builtin_key` (`4k`, `1080p`, `720p`; unique when non-null)
- `is_builtin`
- `resolution`, `resolution_weight`
- `target_score` (minimum 20)
- `max_score`
- `revision`
- `updated_at`
- `criteria_json` (versioned JSON)

`criteria_json` shape:

```json
{
  "version": 1,
  "quality_options": [{"value": "web-dl", "label": "WEB-DL", "weight": 10}],
  "video_codecs": [],
  "audio_codecs": [],
  "audio_languages": [],
  "audio_channels": [],
  "subtitle_formats": [],
  "subtitle_languages": []
}
```

Builtins are inserted/repaired by `db.ensure_builtin_profiles()` and are
immutable. `settings.default_profile_key` defaults to `1080p`. Existing
movies/series are reassigned to 1080p on upgrade. Old profiles are discarded;
there is deliberately no profile migration.

### Library/catalog

- `items.imdb_id` plus indexes on `(kind, tmdb_id)` and `(kind, imdb_id)`.
- `movies.file_score`, `series_episodes.file_score`.
- `downloads.score`, `downloads.score_details`.
- Nullable per-item overrides: `movies`/`series` `candidate_batch_size`,
  `probe_batch_size`, `search_interval_hours`.

### Bworker

`worker_jobs` remains the imperative durable queue for syncs, downloads,
manual searches, metadata refreshes, probes and scan imports. The bworker
claims those first.

`bworker_work` is the declarative automatic-work schedule. One row per unit,
with `work_key` unique, `work_type`, polymorphic `entity_type`/`entity_id`,
`payload`, `enabled`, `stage`, `status`
(`pending|running|retry|failed_stopped|disabled|complete`), retry fields,
`next_run_at`, opaque `cursor`, best-candidate identity/score, profile
revision, `current_download_id`, `reset_requested`, and timestamps.

`bworker_state` is the singleton pause/current-work authority.
`bworker_policies` is the per-work-type toggle/retry policy.
`bworker_events` is durable per-entity work history, pruned to the newest 15
rows per `(entity_type, entity_id)` by its writer.
`bworker_scan` and `bworker_candidates` are derived candidate-paging state and
are excluded from backups.

Work keys:

- `movie:<movie_id>:search`
- `episode:<episode_id>:search`
- optional series/global keys: `series:<series_id>:search`, `global:<type>`

Default policies:

| work_type | enabled | max failures | retry |
|---|---|---|---|
| movie_search | 1 | infinite | 21600s |
| series_search | 1 | infinite | 14400s |
| episode_search | 1 | infinite | 14400s |
| playlist_sync | 1 | infinite | 300s ×2 cap 3600 |
| metadata_refresh | 1 | infinite | 604800s |
| download | 1 | 3 | 60s ×2 cap 900 |
| probe | 1 | 3 | 300s |
| library_scan | 1 | 3 | 900s ×2 cap 900 |
| activity_cleanup | 1 | n/a | always enabled |

## 2. Bworker loop and retries

1. Housekeeping: recover orphaned jobs/work, heartbeat, trim the activity log,
   prune events/jobs.
2. If `bworker_state.paused=1`: write one paused entry, keep housekeeping
   running, do not claim new work, sleep briefly.
3. Materialise due periodic work and claim one `worker_jobs` row first.
4. If no job, claim one due `bworker_work` row.
5. Run the handler. Update stage/progress/events.
6. On success: schedule the next run or mark complete.
7. On transient failure: increment `failure_count`; retry with backoff unless
   the policy limit is reached, then set `failed_stopped`. A profile rejection
   is a normal result, not a failure.
8. Reset sets `failure_count=0`, `status=pending`, `stage=pending`,
   `next_run_at=now`, clears error/best/cursor, and is picked up next loop.
   Per-item and global reset exist.
9. Timing: due work runs immediately. If idle and elapsed ≤10s, sleep 30s; if
   elapsed >10s, skip the idle wait once.

Pause finishes the current bounded unit (at most three probes / active
download) and never interrupts import/rename/move. Manual acquisition returns
409 while paused. Auto-work downloads use `max_attempts=1`; bworker owns their
retries, so downloader and bworker retry counts do not multiply.

Stages used by UI/events:

`pending`, `waiting_availability`, `waiting_air`, `search`, `searching_candidates`,
`probing`, `downloading`, `verifying`, `renaming`, `moving`, `awaiting_upgrade`,
`complete`, `no_candidates`, `failed`, `paused`, `skipped`.

## 3. Profile scoring

Mandatory: resolution (exact, or lower only when upgrades=1) and at least one
selected quality/source. Both are required for eligibility.

Base score = `resolution_weight + best matching source weight` (defaults 20).
Optional sections add:

- exclusive (best match only): video codec, audio codec, audio channels;
- multi-valued (each unique match adds its weight): audio languages, subtitle
  languages, subtitle formats.

`max_score` = mandatory maximum + all optional maxima. Enforce
`20 <= target_score <= max_score`.

`target_met` = eligible AND score >= target_score AND exact selected
resolution. Choose the highest-scoring target_met candidate; if none, choose
the highest-scoring eligible fallback. Lower-resolution fallbacks are
downloaded only after the search pool is exhausted and are marked
`awaiting_upgrade`; re-search on the section interval and upgrade only when a
strictly better score appears. Current files are re-scored from stored
`media_info` when the profile changes.

Tie-break: exact resolution, highest source weight, title/year score, size.

## 4. Candidate paging

- Resolve by TMDB id first, then IMDb id, then title/year/alternative titles.
- Use keyset pagination (`id > cursor ORDER BY id`), never offset.
- A scan has a query fingerprint and catalog epoch. A changed title/profile or
  a catalog sync invalidates the cursor; the probe cache remains valid.
- Discover at most 25 new candidates per scope per iteration. Probe at most 3
  pending candidates per bworker iteration, one subprocess at a time.
- Deduplicate by `(source_id, provider_kind, provider_remote_id,
  episode_stream_id)`.
- Pool exhausted means every query and candidate is finished. Never select a
  stale/deleted catalog item or re-download the identity that produced the
  current file.

## 5. Activity log

Valkey list, written by bworker only. Key `iptv-charts:activity` plus an id
counter. Entry JSON:

```json
{
  "id": 12, "event": "work", "level": "info",
  "work_id": 4, "work_type": "movie_search",
  "target": {"kind": "movie", "id": 4, "label": "Movie"},
  "stage": "probing", "status": "running",
  "message": "Probing candidate 2/25",
  "progress": {"done": 2, "total": 25},
  "started_at": 1700000000, "finished_at": null,
  "next_run_at": null
}
```

Push and trim atomically under one Lua script: after push, if length >= 500,
`LTRIM 0 99`. Client timeouts are short; any Valkey error is caught and never
fails work. The web can show a degraded log and current work from SQLite.
Progress writes are throttled to stage changes / roughly once per second.

## 6. Settings keys

Added defaults: `external_player_enabled=0`, `default_profile_key=1080p`,
`movie_search_interval_hours=6`, `series_search_interval_hours=4`,
`candidate_batch_size=25`, `probe_batch_per_loop=3`, `update_check_enabled=1`,
`bworker_retry_delay_seconds=60`, `bworker_retry_backoff=2.0`,
`bworker_retry_max_delay_seconds=3600`, `bworker_idle_wait_seconds=30`,
`bworker_fast_loop_seconds=10`, `activity_log_cap=500`,
`activity_log_trim_to=100`, `activity_refresh_seconds=5`.

Section settings pages own their keys; global settings owns metadata,
backup/restore, profiles, scan, global refresh and playlist refresh.

## 7. Backup v2

Writes v2, reads v1/v2. `TABLE_INTRODUCED` gates missing table files. Base
tables are always required. Archived builtins are never trusted: canonical
builtins come from code. Pre-v5 archives ignore archived profiles and assign
everything to 1080p. V2 archives remap builtin and custom profile ids.
`bworker_work` is reset on restore and rebuilt for monitored items if absent;
events are trimmed to 15. Derived scans/candidates, probes, worker queue and
Valkey activity are excluded. Restore refuses while bworker is running or an
active download exists; a paused bworker is safe. New settings defaults are
ensured inside the restore transaction.

## 8. API conventions

- Blueprints return `{"ok": true, ...}` / `{"ok": false, "error": ...}`.
- Expected errors map to 400/404/409/502/503 as today; do not leak provider
  URLs or secrets.
- All writes remain protected by the existing loopback Host/Origin guard.
- New bworker API: `/api/bworker/status`, `/pause`, `/resume`, `/activity`,
  `/policies`, `/reset`.
- No frontend CDN. Font Awesome/Bootstrap are vendored locally.
- No Vue or frontend build step.

## 9. Ownership

- Foundation: `schema.sql`, `db.py`, `backup.py`.
- Profiles: `quality.py`/new profile model, profile routes/UI.
- Bworker: `bworker.py`, `iptv_charts/bworker.py`, `jobs.py`, `activity_log.py`, `bworker_api.py`, `scheduler.py`.
- Acquisition: `matching.py`, `items.py`, `probe.py`, `library.py`, provider identity extraction.
- Item stages/events: bworker event helpers and stage/history APIs.
- Settings/UI/Explore/Import/Storage/Container/Deploy/Release: separate agents.
- Shared `app.py`, `manager_api.py`, `manager_web.py`, `library.py` and
  templates are integration-owned; feature agents must not make unrelated
  edits there.

Tests: each feature adds a standalone `tests/<feature>.py`; final integration
runs all suites plus a container smoke test.
